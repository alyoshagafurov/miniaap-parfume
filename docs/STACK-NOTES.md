## Admin auth library choice for Next.js 16 two-path login (Telegram Mini App initData + argon2id password; browser password + Telegram-DM'd 6-digit OTP), OWNER/EDITOR roles enforced in Server Actions, Redis-backed rate limits, self-hosted on a Russian VPS

**Decision.** Use better-auth@1.7.5. It is the only one of the three that is simultaneously stable-tagged, declares Next 16 + React 19 in its peerDependencies, and ships first-class primitives for every requirement instead of making you build them: the two-factor plugin's otpOptions gives 6 digits / 5-minute TTL / 5 attempts / hashed-at-rest OTP with a sendOTP(user, otp) callback you point at your Telegram bot (exactly Path B), accountLockout gives 5 failures per 900s natively, secondaryStorage + rateLimit.storage:"secondary-storage" puts both sessions and rate limiting in your own Redis with no third-party service, session.expiresIn + advanced.defaultCookieAttributes give the 12h httpOnly/Secure/SameSite=Lax cookie, emailAndPassword.password.hash/verify lets you swap the default scrypt for argon2id, and telemetry defaults to false so nothing phones home from the VPS. Install: better-auth@1.7.5, @node-rs/argon2@2.2.1, ioredis@6.0.0, @telegram-apps/init-data-node@2.0.10, plus your existing prisma client. Reject Auth.js v5: npm dist-tag latest for next-auth is still 4.24.15 and v5 is still 5.0.0-beta.32 (published 2026-07-20), it has been in beta since beta.3 in Oct 2023, its own README badge labels the beta tag as "latest", and maintainers give no stable date — shipping a client's admin auth on a ~3-year beta with 3 releases in the last 11 months is the wrong risk. Reject hand-rolled: iron-session@9.0.1 is genuinely Next-16-ready (it exports nextProxyCookies and types against Next's cookies()), but it is only a sealed-cookie primitive — you would hand-build OTP issuance/TTL/attempt-counting, account lockout, rate limiting, password hashing and session revocation, which is several hundred lines of security-critical code better-auth already ships and patches weekly.

**Pitfalls.**

- Unit mismatch in better-auth OTP config: the two-factor plugin's otpOptions.period is in MINUTES (default 3), while the separate email-otp plugin's expiresIn is in SECONDS (default 300). For a 5-minute TTL on the 2FA path you write period: 5, not 300.
- OTPs and verification tokens are stored in PLAIN TEXT by default. Set otpOptions.storeOTP: "hashed" and verification.storeIdentifier: "hashed" or a DB dump leaks live login codes.
- better-auth's rateLimit is only enabled in production by default — set rateLimit.enabled: true explicitly or your staging environment silently has no brute-force protection.
- The Redis secondaryStorage.increment implementation must apply the TTL only when the counter is created (n === 1). If you call EXPIRE on every increment you extend the window on each attempt and the 5-per-15-min limit becomes unreachable/never resets correctly.
- nextCookies() must be the LAST entry in the plugins array; otherwise cookies set during Server Actions are not written.
- React Server Components cannot set cookies. Session refresh and any sign-in/sign-out must happen in a Server Action or route handler, not in an RSC.
- Next.js 16 renamed middleware.ts to proxy.ts and the exported function must be named `proxy`; it now defaults to the Node runtime and is meant as a thin redirect/rewrite layer. Do not put the authorization decision there — the requirement to check roles inside every Server Action is the correct design, and proxy.ts should at most redirect unauthenticated users to /login.
- better-auth defaults to scrypt for password hashing. If you do not override emailAndPassword.password.hash/verify you will not be running argon2id, and switching later invalidates every stored hash.
- @telegram-apps/init-data-node v2 has a different API from v1: the root export pre-binds Node crypto so validate(value, token, opts) works, but the sub-path exports take an injected signData function. Also expiresIn defaults to 86400 (1 day) — pass a short window (e.g. 300) or replayed initData stays valid for a day.
- Path A cannot simply call auth.api.signInEmail: with the two-factor plugin enabled, a user with twoFactorEnabled will get a twoFactorRedirect response instead of a session, which would wrongly demand an OTP inside the Mini App. Use a custom endpoint that creates the session directly (as in the skeleton).
- next-auth v5 is beta and its session mutation API is literally named unstable_update — a rename there is a breaking change you would absorb with no stable-release guarantee.
- iron-session is stateless: there is no server-side revocation, so a stolen sealed cookie is valid until its ttl expires. If you go that route you must add a Prisma session table and check it on every request, which erases most of the 'it's simpler' argument.

## Tailwind CSS v4.3.3 + Next.js 16.3.6 — setup, CSS-first design tokens, locked palette, self-hosted fonts, shadcn/ui

**Decision.** Install exactly `tailwindcss@4.3.3` + `@tailwindcss/postcss@4.3.3` as devDependencies and wire them through PostCSS — NOT `@tailwindcss/vite` (Next does not use Vite) and NOT `@tailwindcss/webpack` (exists since 4.2.0 but Next 16 defaults to Turbopack; PostCSS is the path both Next 16.3.6 and Tailwind document). There is no Next-specific Tailwind plugin. Create `postcss.config.mjs` with a single `@tailwindcss/postcss` entry, and put `@import "tailwindcss";` at the top of `app/globals.css`, imported once from `app/layout.tsx`. Author all design tokens CSS-first: one `@theme` block that STARTS with `--color-*: initial;` to delete the entire default palette, then your brand ramps; a second `@theme inline` block for font families that point at `next/font/local` variables. The `--color-*: initial` reset is mandatory and non-negotiable for your grep-ability requirement, because Tailwind 4.2.0 added `olive`, `mauve`, `mist` and `taupe` to the DEFAULT palette — `--color-olive-600` already exists as `oklch(46.6% 0.025 107.3)`, so your `#4D5527` would silently override a built-in and `bg-olive-400`/`bg-olive-900` would keep resolving to Tailwind's greys instead of failing. For fonts, note that `next/font/local` does NOT accept a `subsets` option (google-only), so you must pre-subset the variable woff2 to latin+cyrillic yourself with `pyftsubset` and pass `variable: '--font-...'`. shadcn/ui is current (CLI `shadcn@4.21.0`, `npx shadcn@latest init`) and fully supports Tailwind v4 + React 19; its `baseColor` list now even includes the new `olive`/`mauve`/`mist`/`taupe` families — but do not run it against a palette-wiped theme without adding back the semantic tokens it expects, and leave `tailwind.config` blank in `components.json`.

**Pitfalls.**

- FATAL for your grep requirement: `olive` is a BUILT-IN Tailwind family since 4.2.0 (`--color-olive-600: oklch(46.6% 0.025 107.3)`). Without `--color-*: initial`, your `--color-olive-600: #4D5527` merely overrides one shade while `bg-olive-50…950` keep resolving to Tailwind's desaturated greys — stray colors compile silently and grep finds no hex. Same trap for mauve, mist, taupe.
- `--color-*: initial` must be the FIRST declaration inside the `@theme` block; anything defined before it in the same block is wiped too.
- Wiping colors removes `--color-white`/`--color-black`, so `bg-white`, `text-black`, and any `border-white/10` break. Re-declare both explicitly.
- Do not use `--*: initial` unless you mean it — it also deletes `--spacing`, which kills p-_, m-_, gap-_, w-_, h-* and every breakpoint. Prefer per-namespace resets (`--color-*`, `--font-*`, `--radius-*`).
- `@theme` vs `@theme inline`: use plain `@theme` for literal values; use `@theme inline` whenever the value is `var(--something-else)` (like a next/font variable), otherwise the utility emits `var(--font-sans)` which resolves to `var(--font-app-sans)` at the wrong scope and silently falls back.
- `:root` variables do NOT generate utilities — that is the point. Put runtime/layout values (Telegram viewport height, header offsets) in `:root`, design tokens in `@theme`.
- Tailwind tree-shakes unused theme variables out of the emitted `:root`. If JS reads a token via `getComputedStyle` (e.g. feeding colors to a Telegram WebApp theme call), that variable may not exist in the CSS. Use `@theme static` to force emission.
- `next/font/local` silently ignores `subsets` — passing it does nothing. The file you ship IS the subset, so a full Cyrillic variable font will be served in its entirety unless you run pyftsubset yourself.
- Applying the font `.variable` class to `<body>` instead of `<html>` means `html { font-family }` and any `@theme inline` font token resolving at the root will be undefined. Put it on `<html>`.
- Arbitrary values bypass the locked palette: `bg-[#ff0000]` and `text-[rgb(1,2,3)]` still compile after `--color-*: initial`. Only a lint/grep rule catches these — include `\[#...\]` and `rgb(`/`hsl(`/`oklch(` in the scan.
- shadcn init writes semantic tokens (`--background`, `--foreground`, `--primary`, …) mapped through `@theme inline`. If you ran `--color-*: initial` first, its generated component classes referencing e.g. `border-input` still work, but any component using a raw default color will now fail to compile — audit after `npx shadcn@latest add`.
- `start-*`/`end-*` utilities are deprecated since 4.2.0 in favour of `inset-s-*`/`inset-e-*` — relevant if you support RTL.

## Next.js 16.3.6 App Router — data caching & revalidation API (Cache Components, 'use cache', cacheTag/cacheLife, updateTag/revalidateTag) for a Prisma-backed wholesale catalog

**Decision.** Install `next@16.3.6` (verified current `latest` on npm as of 2026-09-22; `canary` is 16.4.0-canary.38) with `prisma@7.10.0` / `@prisma/client@7.10.0`. Enable Cache Components by setting the TOP-LEVEL `cacheComponents: true` in `next.config.ts` — `experimental.dynamicIO` and `experimental.useCache` were REMOVED in 16, and `experimental.ppr` / `export const experimental_ppr` are gone (PPR is now implied by `cacheComponents`). `'use cache'` is stable-as-a-feature but gated behind that flag; `cacheTag()` throws `E886` ("only available with the `cacheComponents` config") if `__NEXT_USE_CACHE` is unset. Import `cacheTag` and `cacheLife` from `next/cache` WITHOUT the `unstable_` prefix (the prefixed aliases still exist but `console.error` a deprecation on first call). Do NOT use `unstable_cache` for new code — it still ships and works, but the shipped doc says it "has been replaced by `use cache` in Next.js 16". Pattern: put `'use cache'` + `cacheLife('<profile>')` + `cacheTag(...)` directly inside plain async Prisma query functions in `lib/`, keyed by their arguments; invalidate from admin Server Actions with `updateTag(tag)` (Server-Action-only, immediate expiry, read-your-own-writes — exactly what an admin edit screen needs) and from webhooks/Route Handlers with `revalidateTag(tag, 'max')` or `revalidateTag(tag, { expire: 0 })`. The single-arg `revalidateTag(tag)` form is deprecated and now a TS error — the second parameter is non-optional in the shipped `.d.ts`. Because `use cache` stores in-memory by default and does NOT persist across serverless instances or deploys, on a serverless host add `'use cache: remote'` (with a `cacheHandlers` handler) for the hot catalog queries, or self-host so the LRU actually persists. Critical Prisma interop: `Decimal` is a class instance and class instances are NOT serializable as `'use cache'` return values — map prices to `string`/`number` inside the cached function before returning.

**Pitfalls.**

- `revalidateTag(tag)` with one argument is now a TYPE ERROR — `profile` is non-optional in the shipped `revalidate.d.ts`. At runtime it still works but console-warns and behaves like `{ expire: 0 }`. Every existing call site needs a second argument or a switch to `updateTag`.
- Prisma `Decimal` is a class instance, and class instances are explicitly unsupported as `'use cache'` return values. A wholesale catalog is full of `Decimal` prices — `return prisma.product.findMany(...)` straight out of a cached function will fail serialization. Map `Decimal -> string` (or `Number`) inside the cached function. `BigInt` and `Buffer`/`Bytes` fields need the same treatment; `Date` is fine.
- Do NOT pass the `params` or `searchParams` Promise into a `'use cache'` function. It does not error immediately — it hangs the build for 50 seconds and then throws "Filling a cache during prerender timed out". Await outside, pass the resolved primitives in.
- `cookies()` / `headers()` inside a cached scope fails with `next-request-in-use-cache`, and the check follows the call stack — a shared `getSession()` helper called from inside `'use cache'` trips it. On a dynamically rendered route this can pass `next build` and only blow up under `next start`. For a Telegram Mini App this bites hard: initData lives in headers/cookies, so keep all auth/session reads outside cached storefront queries.
- Every distinct serialized argument shape creates its own cache entry. `getCategoryProducts(slug, filters)` with free-form filters (price ranges, multi-select brands, page numbers) explodes cardinality and drives hit rate toward zero. Normalize and clamp the filter object (sort arrays, dedupe, whitelist `sort`, cap `perPage`) before calling, and consider caching only the unfiltered/first-page listing while streaming filtered results uncached inside `<Suspense>`.
- Filter key ORDER and `undefined`-vs-absent keys can change the serialized argument and therefore the cache key. Always build the filter object through a single `normalizeFilters()` that returns the same key set in the same order with no optional properties. (I did not verify key-order sensitivity in the serializer directly — treat the normalizer as cheap insurance.)
- `use cache` stores in-memory by default and the cache key contains the build ID, so NOTHING survives a deploy, and on serverless each instance has its own cold LRU. A catalog cached this way will re-hit Postgres constantly on Vercel-style hosting. Either self-host (entries persist, tune `cacheMaxMemorySize`) or add `'use cache: remote'` plus a `cacheHandlers` implementation for the hot queries.
- `updateTag()` throws E872 in Route Handlers, Client Components, and anywhere that is not a Server Action — the guard literally checks `workStore.page.endsWith('/route')`. Webhook-driven invalidation must use `revalidateTag(tag, 'max')` or `revalidateTag(tag, { expire: 0 })`.
- `revalidateTag` / `revalidatePath` / `updateTag` throw if called during render (E7), inside any `'use cache'` scope (E181), inside `unstable_cache` (E306), or inside `generateStaticParams` (E1127). Keep all invalidation in the action/handler body, never in a data function.
- Any of these called from a Server Action wipes the ENTIRE client router cache for that user, not just the tagged entries — so a chatty admin save action degrades that admin's whole navigation experience. Batch invalidation into one action rather than firing several.
- Enabling `cacheComponents` is not a rename of the old flags: uncached data or runtime APIs outside `<Suspense>` become build/dev errors. `dynamic`, `revalidate`, `fetchCache` and `dynamicParams` segment exports stop being accepted, `generateStaticParams` returning `[]` errors, and awaiting `params` at the top of a page kills the static shell. Budget a real migration pass, not a config edit.
- `cacheLife('seconds')` (and any profile with `expire` < 5 min or `stale` < 30 s) is excluded from prerenders entirely, and nesting such a cache inside a `use cache` that has no explicit `cacheLife` is a prerender-time build error. Always call `cacheLife()` explicitly in every cached function.

The disqualifier is not performance or semantics — it is that TS 7.0.2 deliberately ships no programmatic compiler API: `require("typescript")` returns literally `{version, versionMajorMinor}` (verified at runtime), `typescript/lib/typescript.js` is not exported, and there is no `tsserver`. typescript-eslint therefore declares the peer range `typescript: ">=4.8.4 <6.1.0"` on BOTH latest (8.70.1) and canary (8.70.2-alpha.4), i.e. TS 7 is excluded with no canary escape hatch. Since this project requires ESLint, TS 7 is off the table today regardless of its 8-12x speed win. TS 5.9.3 is the vendor-blessed greenfield baseline: create-next-app@16.3.6 — the exact CNA matching your Next version — writes `typescript: "^5"` into every generated package.json, so 5.9.3 is what every new Next 16 project resolves to and is the most-tested path with React 19 and Prisma 7 (@prisma/client@7.10.0 peer is `typescript: ">=5.4.0"`). Write the tsconfig TS7-clean from day one (no `baseUrl`, target >= ES2015, no `downlevelIteration`, `moduleResolution: "bundler"`) — the CNA template already is, and I verified it compiles clean under both 6.0.3 and 7.0.2. Then schedule a separate, low-risk bump to TypeScript 6.0.3 (a real stable release, 2026-04-16, not just the `beta` dist-tag): it keeps the full API + tsserver, is inside typescript-eslint's `<6.1.0` peer range, is what Next's own missing-dependency path tells you to install (`typescript@^6.0.0`), and converts every TS7 removal into a deprecation error you can fix ahead of time. Revisit TS 7 only once TS 7.1 ships the new API and typescript-eslint widens its peer range.

**Pitfalls.**

- TS 7.0.2 has NO programmatic compiler API. `require("typescript")` returns only `{version, versionMajorMinor}` — verified at runtime. Anything doing `ts.createProgram`, `ts.SyntaxKind`, `ts.transpileModule`, or `ts.LanguageService` silently gets `undefined` and crashes. This breaks typescript-eslint, ts-jest, ts-node, tsc-alias, many bundler plugins, and Vue/Svelte/Astro/MDX/Angular tooling.
- typescript-eslint is the hard blocker, not Next.js. Peer is `>=4.8.4 <6.1.0` on latest AND canary. Installing TS 7 produces an ERESOLVE peer conflict, and forcing past it with --legacy-peer-deps gives a runtime crash, not a graceful degradation.
- Do NOT confuse 'Next.js supports TS 7' with 'the project supports TS 7'. Next 16.3.6 genuinely handles TS7 (useTypeScriptCli defaults to true and it shells out to the tsc CLI) — but that only covers `next build` type-checking. It does not rescue ESLint.
- TS 7 ships no tsserver (no lib/tsserver.js, no bin/tsserver) — it moved to LSP. The `"plugins": [{"name": "next"}]` entry in the CNA tsconfig is a classic tsserver plugin, so the Next editor integration degrades under TS7 depending on your editor's LSP support.
- `typescript/lib/lib.dom.d.ts` does not exist under TS 7 — the stdlib moved into the per-platform binary package (@typescript/typescript-darwin-arm64 etc.). Any tool or config resolving that path breaks.
- `npm i prisma@latest` today installs prisma@8.0.0-rc.15, a release candidate published to the `latest` dist-tag. For Prisma 7 you must pin 7.10.0 explicitly (or use the `prev` tag). @prisma/client@latest is correctly 7.10.0.
- TS 6 turns deprecated options into ERRORS (TS5101/TS5107), not warnings — e.g. `baseUrl` fails the build unless you set `"ignoreDeprecations": "6.0"`. Don't assume a TS5→TS6 bump is a no-op on an existing tsconfig.
- If you ever do move to TS 7: `baseUrl` is removed (TS5102) — replace with `"paths": {"*": ["./*"]}`; `target: ES5` is removed (TS5108); `downlevelIteration`, `module: amd/umd/system`, and `moduleResolution: node/node10/classic` are all removed. Write the tsconfig without them now so the migration is a version bump.
- TS 7 is ESM-only (`"type": "module"`) and its `tsc` bin is an extensionless ESM wrapper that Node 20.9 cannot use as a main entry — Next works around this by invoking `lib/tsc.js` directly. Custom scripts that call `node node_modules/typescript/bin/tsc` may fail.
- Don't run a 'TS 7 with 5.x fallback' dual-compiler setup as the primary plan: it means CI green under one compiler and unknown under the other, and it doubles the surface where `strict` diagnostics can diverge. Use TS7 only as an extra non-blocking informational CI job.

## Prisma 7 (client 7.10.0) + PostgreSQL 16 + Next.js 16 + pg_trgm fuzzy search — current API as of 2026-09-22

**Decision.** Pin EXACT versions — do not use `npm i prisma` (the `latest` dist-tag is `8.0.0-rc.15`, a release candidate, so a bare install pulls an RC into production). Install `prisma@7.10.0`, `@prisma/client@7.10.0`, `@prisma/adapter-pg@7.10.0` (all exact, no caret), plus `pg@^8.16.3` and `tsx` as devDeps. 7.10.0 is the correct stable: it is `latest` for `@prisma/client` and `@prisma/adapter-pg`, and `prev` for the `prisma` CLI. Use the `prisma-client` generator with an explicit `output` (the legacy `prisma-client-js` is labelled "Legacy" inside the 7.10.0 CLI itself) and import `PrismaClient`/`Prisma` from `<output>/client`. A driver adapter is now REQUIRED — `PrismaClientOptions` is a union of `{adapter}` | `{accelerateUrl}`, so bare `new PrismaClient()` will not type-check or run. Move the DB URL out of schema.prisma into `prisma.config.ts` (with `import "dotenv/config"`, since env vars are no longer auto-loaded), and put the seed command in `migrations.seed` (the `package.json#prisma.seed` key is gone). For search, do NOT use a Postgres generated column — Prisma cannot model it and `migrate dev` will try to "fix" it into a plain DEFAULT column. Instead use a plain `String` column maintained by a BEFORE INSERT OR UPDATE trigger installed via raw SQL in a migration, indexed with `@@index([searchNorm(ops: raw("gin_trgm_ops"))], type: Gin)` — that index IS expressible in Prisma schema, so there is no drift. Filter with the `%` operator (GIN-accelerated) and sort with `similarity()` (a plain sort; GIN cannot do KNN ordering). Do all ё/е and case folding inside an IMMUTABLE SQL function applied to BOTH the stored column and the query string, never in app code only.

**Pitfalls.**

- `npm i prisma` installs 8.0.0-rc.15, because Prisma has pointed the CLI's `latest` dist-tag at a release candidate while `@prisma/client`'s `latest` is still 7.10.0 stable. A plain install therefore yields a CLI/client major-version skew. Pin with `-E` and verify with `npx prisma -v` after install.
- prisma.io unversioned doc URLs now render Prisma ORM 8 content, including a completely different fluent query API (`db.orm.public.Post.orderBy(...).limit(20).all()`). Anyone reading /docs/orm/... without the /v7/ segment will write code that does not exist in 7.10.0. Always link /docs/orm/v7/.
- Do NOT model the normalized search column as a PostgreSQL `GENERATED ALWAYS AS (...) STORED` column. Prisma has no representation for it, emits `DEFAULT` instead, and `migrate dev` will attempt to rewrite the column — permanent drift plus a failing migration. Use the trigger-maintained plain column.
- `unaccent()` is STABLE, not IMMUTABLE, so it cannot be used directly in a generated column or index expression; you get `ERROR: functions in index expression must be marked IMMUTABLE`. `ALTER FUNCTION unaccent(text) IMMUTABLE` needs superuser and breaks on managed Postgres (Azure Flexible Server, Neon, RDS). Use the `immutable_unaccent` SQL wrapper that pins the dictionary name.
- A GIN trigram index does NOT accelerate `ORDER BY similarity(...)` / `<->` — only GiST supports KNN ordering. If you write `ORDER BY "searchNorm" <-> $1 LIMIT 24` with no `%` filter, you get a full sequential scan plus a sort over every row. Filter with `%` first so the GIN index produces a small candidate set, then sort.
- Writing `WHERE similarity("searchNorm", $1) > 0.3` instead of `WHERE "searchNorm" % $1` silently bypasses the GIN index — it is a function call in a filter, not an indexable operator. EXPLAIN will show `Seq Scan` + `Filter:` rather than `Bitmap Index Scan`.
- `pg_trgm.similarity_threshold` is per-session state. With a pg connection pool, a bare `SET` leaks to whichever request next borrows that connection. Use `set_config(..., true)` (transaction-local) inside `prisma.$transaction`, which pins a single connection for the duration.
- The query string must go through the exact same folding as the stored column, or 'Ёлка'/'ЁЛКА'/'елка' will not match. Call `norm_search($1)` in SQL on both sides rather than normalizing in TypeScript — a JS reimplementation will drift from the SQL one the first time either changes.
- `Int` is PostgreSQL `integer`, capping a kopecks column at 2,147,483,647 = 21,474,836.47 RUB. Individual perfume prices are safe, but order totals, lifetime revenue and `_sum` aggregates are not. Postgres `sum(integer)` returns `bigint`, which Prisma types as `number` — an aggregate above 2^53 loses precision silently. Use `BigInt` for any accumulating money column.
- `$queryRaw<T>` returns `T`, not `T[]`. Writing `$queryRaw<SearchRow>` type-checks and then hands you an array at runtime. Always write `$queryRaw<SearchRow[]>`.
- `$queryRaw` returns Postgres `bigint` as JS `BigInt`, so `SELECT count(*)` blows up the moment it reaches `JSON.stringify`. Cast with `::int` in SQL.
- `Prisma.raw()` is a textual splice with no parameterization — it is the one SQL-injection vector in the raw API. Never pass user input through it. Bind values must be template interpolations (`${value}`), which become real placeholders; identifiers (table/column names) cannot be parameterized at all, so validate them against an allowlist.

**Decision.** Install exactly: `grammy@1.46.0`, `@grammyjs/auto-retry@2.0.2`, `@grammyjs/files@1.2.0` (only if you download files), `@grammyjs/transformer-throttler@1.2.1` (only if you fan out notifications). Wire `autoRetry()` via `bot.api.config.use()` with an explicit `maxRetryAttempts` and `maxDelaySeconds` (defaults are `Infinity` and will hang your process). **Pitfalls.**

- `middleware.ts` silently does nothing useful going forward — Next 16 renamed it to `proxy.ts` with an exported `proxy()` function. If you write CSP logic in middleware.ts you may get deprecation behavior rather than what you expect. Run the codemod.
- CSP nonce forces every page dynamic. ISR is disabled, CDN caching is off, and PPR is explicitly incompatible. For a storefront this is a real traffic cost. Consider: nonce only on authenticated/admin routes via the matcher, and static CSP (no nonce) or the experimental `experimental.sri` hash-based CSP for cacheable storefront pages.
- Setting the CSP only on the RESPONSE gives you no nonce. Next reads it from the inbound REQUEST headers (app-render.js line 209), which is why you must pass it through `NextResponse.next({ request: { headers } })`.
- If you emit BOTH `content-security-policy` and `content-security-policy-report-only`, Next reads the nonce from the enforcing header only (`||` short-circuit). Mixed enforce+report-only setups can end up with the nonce keyed to the wrong policy.
- Server Action CSRF is silently bypassed by a request with NO Origin header — Next logs a warning and proceeds. Anything that strips Origin (some proxies, some crawlers, curl) gets through. Block Origin-less Server Action POSTs at Caddy.
- Next prefers `x-forwarded-host` over `host` unconditionally for the CSRF comparison, and takes the first comma-separated value. If Caddy APPENDS rather than OVERWRITES X-Forwarded-Host, an attacker-supplied value lands first and defeats the check. Use `header_up X-Forwarded-Host {host}`, not `+X-Forwarded-Host`.
- Adding a wildcard to `serverActions.allowedOrigins` weakens CSRF broadly. Note `*` matches exactly one label and `**` only at the start; a bare `*`/`**` is rejected; ports cannot be wildcarded. Behind Caddy you should need NO entries at all — if you find yourself adding one, the proxy headers are misconfigured.
- `experimental.proxyClientMaxBodySize` (default 10MB) TRUNCATES oversized bodies silently — no error, no rejection, the handler just sees partial data. With a 10MB upload target you are sitting exactly on the default. Exclude `api` from the proxy matcher AND raise the limit.
- `serverActions.bodySizeLimit` applies to the RAW body including multipart boundaries and part headers, so a 10MB file needs more than a 10MB limit (docs suggest 10-20KB headroom). Better: do not raise it at all — use a Route Handler, since the limit is global to every action.
- Route Handlers get NO automatic CSRF protection. Moving uploads off Server Actions means you must do the Origin/Host check yourself.
- `images.qualities` is now REQUIRED in Next 16. Omitting it silently falls back to [75] and any `quality` prop outside the list gets coerced (or 400s on a direct optimizer hit).
- sharp strips EXIF by default — including the orientation tag. If you do not call `.rotate()` (or `.autoOrient()`) FIRST, phone photos come out sideways with no way to recover.
