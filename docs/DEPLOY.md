# Развёртывание на Railway

Для Алишера. Пошагово, от пустого проекта до работающего каталога.

Что собрать заранее — [ЧТО-НУЖНО.md](../ЧТО-НУЖНО.md).

Если из России витрина будет открываться медленно, есть запасной вариант —
свой сервер в РФ, [приложение в конце](#запасной-вариант--свой-сервер-в-рф).

---

## Схема

```
  покупатель ──https──▶ web (Next.js) ──┬──▶ postgres
                                        ├──▶ redis
                                        └──▶ bucket (фотографии)
                                              ▲
  Telegram ◀──https── bot (long polling) ─────┘
```

Четыре сервиса в одном проекте Railway. Домен, сертификат и HTTPS — от
платформы, своего домена не нужно. Бот ходит в `api.telegram.org` напрямую.

---

## 1. Проект и сервисы

Установите CLI и войдите:

```bash
npm i -g @railway/cli
railway login
```

Создайте проект и свяжите с ним папку репозитория:

```bash
railway init          # назовите проект arumi
railway link
```

Дальше всё описано в [.railway/railway.ts](../.railway/railway.ts) — четыре
сервиса, их переменные и связи между ними:

```bash
railway config plan     # покажет, что будет создано и изменено
railway config apply    # применит после подтверждения
```

`plan` ничего не меняет. Посмотрите список и только потом применяйте.

> **Файл не проверялся против живого Railway.** У меня нет доступа к аккаунту,
> поэтому он написан по документации, а не отлажен. `plan` покажет расхождение,
> если оно есть, и ничего не сломает. Если план не сойдётся — сервисы создаются
> в интерфейсе за десять минут, а все команды и переменные ниже те же самые.

## 2. Переменные

Часть задаётся автоматически — `DATABASE_URL`, `REDIS_URL`, ключи бакета.
Остальное вы вписываете руками в интерфейсе Railway, в разделе Variables
каждого сервиса. **В репозитории их нет и быть не должно.**

**Одна переменная должна стоять раньше первой сборки — `RAILWAY_DOCKERFILE_PATH`.**
В репозитории два Dockerfile, и без неё оба сервиса соберут корневой: бот
получил бы образ витрины и упал бы на старте, потому что команды `pnpm bot` в
нём нет. `railway config apply` её проставляет, но если вы создаёте сервисы
руками — задайте до того, как нажмёте Deploy:

| Сервис  | `RAILWAY_DOCKERFILE_PATH` |
| ------- | ------------------------- |
| **web** | `Dockerfile`              |
| **bot** | `Dockerfile.bot`          |

Для **web** и **bot** одинаково:

| Переменная      | Что это                                                                      |
| --------------- | ---------------------------------------------------------------------------- |
| `BOT_TOKEN`     | Токен от @BotFather. Только здесь, больше нигде                              |
| `BOT_USERNAME`  | Имя бота без собаки                                                          |
| `ADMIN_CHAT_ID` | Чат, куда падают уведомления о заявках                                       |
| `AUTH_SECRET`   | Подписывает сессии админки. `openssl rand -base64 32`                        |
| `MINI_APP_URL`  | Адрес, который Railway выдал сервису **web**, со схемой и без слэша на конце |

Необязательные:

| Переменная                      | Что это                                                                                                |
| ------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `TELEGRAM_API_ROOT`             | Пусто — значит напрямую в Telegram. Заполняется, только если каталог переедет в РФ и понадобится релей |
| `NEXT_PUBLIC_YANDEX_METRICA_ID` | Номер счётчика Метрики. Пусто — Метрика не грузится вовсе                                              |

`MINI_APP_URL` появляется только после первого деплоя web — Railway выдаёт
адрес сервису при создании. Впишите его и передеплойте оба сервиса.

## 3. Схема и проверка

Миграции накатывает сервис **bot** в `preDeploy` — у него полный образ с
исходниками и prisma CLI, а у витрины образ standalone, в котором ни того, ни
другого нет. На самом первом развёртывании прогоните их руками, чтобы витрина
не поднялась раньше схемы:

```bash
railway run --service bot sh -c 'DATABASE_URL=$DATABASE_PUBLIC_URL pnpm prisma migrate deploy'
```

Дальше они применяются сами при каждом деплое бота.

```bash
railway run --service web pnpm deploy:check
```

Проверяет то, что ломается молча: переменные, локаль базы, миграции, Redis,
права на запись в бакет и доступность Telegram. Печатает, что делать с каждой
проблемой.

### Если ругается на локаль базы

Самое важное место во всём развёртывании.

Под `LC_CTYPE=C` расширение pg_trgm извлекает из кириллицы **ноль** триграмм:
поиск с опечаткой по-русски перестаёт работать полностью, а по-латински
продолжает — то есть дефект не виден, пока кто-нибудь не наберёт «шанел».

Локаль задаётся при создании базы и потом не меняется. На Railway до `initdb`
не добраться, но можно создать **отдельную базу** в том же кластере:

```bash
railway run --service web pnpm db:create-ru
```

Затем в переменных **web** и **bot** замените имя базы в `DATABASE_URL` на
`arumi` и прогоните миграции:

```bash
railway run --service web pnpm prisma migrate deploy
railway run --service web pnpm deploy:check
```

Проверка также убеждается, что collation `ru-RU-x-icu` не просто числится, а
действительно сортирует: сборка PostgreSQL без ICU показывает её в
`pg_collation` и падает при использовании.

```bash
pnpm brand:banner        # создаст brand/bot-banner.png, 1280×640
```

Загрузить в админке: **Настройки → Баннер приветствия бота**. Без него
приветствие — просто текст, и это тоже нормальный вид.

## 6. Настройка бота в BotFather

С аккаунта клиента, у [@BotFather](https://t.me/BotFather):

1. `/setdomain` → адрес сервиса web
2. `/setmenubutton` → кнопка «Открыть каталог» → тот же адрес

Команды (`/start`, `/catalog`, `/contacts`) бот регистрирует сам при запуске.

---

## 7. Обновление

```bash
git push        # Railway собирает и выкладывает сам
```

Миграции применяются автоматически: они в `preDeploy`, то есть выполняются
один раз между сборкой и запуском, и неудачная миграция останавливает выкладку
вместо того, чтобы поднять приложение на половине схемы.

Если менялись сервисы или переменные — `railway config plan` и `apply`.

## 8. Резервные копии

**Регулярные — от Railway.** Включите бэкапы у сервиса Postgres в интерфейсе.
Они снимаются по расписанию и хранятся без вашего участия. Проверьте, что
включены: это одна галочка, про которую забывают.

**Ручная копия — перед рискованным:**

```bash
railway run --service web ./scripts/dump.sh
```

Кладёт файл в `./backups/`. Забирать копию стоит перед обновлением схемы,
массовым импортом и вообще перед всем, что страшно.

Восстановить:

```bash
pg_restore -d "$DATABASE_URL" --clean --if-exists --no-owner backups/arumi-….dump
```

**Потренируйтесь один раз** на пустой базе. Бэкап, который никто ни разу не
восстанавливал, — это надежда, а не бэкап.

## Что смотреть, когда что-то не так

```bash
railway logs --service web
railway logs --service bot
```

| Симптом                                                     | Обычная причина                                                                                                                                       |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Сборка web падает на «Can't reach database server»          | Не задан `DATABASE_PUBLIC_URL` у сервиса web. Приватная сеть при сборке недоступна, а `next build` в базу ходит — Dockerfile объявляет её через `ARG` |
| Бот запускается и сразу падает                              | Неверный `BOT_TOKEN`, либо Telegram недоступен                                                                                                        |
| Бот падает с «Command "bot" not found» или сразу после сборки | У сервиса bot не задан `RAILWAY_DOCKERFILE_PATH=Dockerfile.bot` — он собрал образ витрины                                                              |
| Поиск не находит по-русски с опечаткой, по-латински находит | Локаль базы не UTF-8 — раздел 3                                                                                                                       |
| Фотографии не показываются                                  | Сервис web не видит бакет: проверьте `S3_*` в его переменных                                                                                          |
| Кнопка каталога в боте ведёт в никуда                       | Не задан `MINI_APP_URL`                                                                                                                               |
| Заявки приходят, уведомлений нет                            | Не задан `ADMIN_CHAT_ID`                                                                                                                              |
| web перезапускается по кругу                                | `/api/health` не отвечает: база недоступна                                                                                                            |

# Запасной вариант — свой сервер в РФ

Если из России витрина будет открываться медленно, всё переезжает на VPS в РФ.
Это готовый и **проверенный запуском** путь: `docker-compose.prod.yml`
поднимается, все сервисы healthy, `deploy:check` проходит.

Отличия от Railway:

- **Нужен релей за пределами РФ** — `api.telegram.org` с российского хостинга
  недоступен. Конфиг и инструкция: [relay/README.md](../relay/README.md).
  Без него не работает ничего телеграмного: ни приветствие, ни уведомления о
  заявках, ни код входа в админку.
- **Нужен свой домен** и две A-записи: на сервер и на релей. Домен обязан
  резолвиться **до** первого запуска — Caddy выпускает сертификат через ACME, а
  тот проверяет, что домен уже ведёт сюда.
- **Нужно объектное хранилище** — Yandex Object Storage, VK Cloud, Selectel.
  С публичным чтением: тогда браузер забирает фотографии напрямую, минуя
  приложение. Адрес бакета кладётся в `NEXT_PUBLIC_S3_PUBLIC_URL`, и прокси
  `/api/media/…` сам собой перестаёт использоваться.

Порядок:

```bash
cp .env.production.example .env.production   # заполнить, chmod 600
./scripts/deploy.sh                          # поднимет всё в правильном порядке
DEPLOY_TARGET=vps docker compose -f docker-compose.prod.yml \
  --env-file .env.production run --rm --entrypoint "" migrate pnpm deploy:check
```

`deploy.sh` существует из-за одного свойства архитектуры: под
`cacheComponents` `next build` выполняет функции с `'use cache'`, наполняя кэш
при пререндере, — то есть сборка витрины обращается к PostgreSQL по-настоящему.
Поэтому сначала база и схема, только потом сборка.

Регулярные копии там делает `scripts/backup.sh` (cron, выгрузка в бакет,
хранение 14 дней), восстановление — `scripts/restore.sh`.
