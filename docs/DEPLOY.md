# Развёртывание на Railway

Для Алишера. Пошагово, от пустого проекта до работающего каталога.

Прод уже развёрнут по этому документу. Что осталось сделать до передачи
клиенту — [ЧТО-НУЖНО.md](../ЧТО-НУЖНО.md).

Если из России витрина будет открываться медленно, есть запасной вариант —
свой сервер в РФ, [приложение в конце](#запасной-вариант--свой-сервер-в-рф).

---

## Схема

```
  покупатель ──https──▶ web (Next.js) ──┬──▶ postgres
                                        ├──▶ redis
                                        └──▶ bucket (фотографии)
                                              ▲
  Telegram ◀──https── bot (long polling) ─────┘
```

Четыре сервиса в одном проекте Railway. Домен, сертификат и HTTPS — от
платформы, своего домена не нужно. Бот ходит в `api.telegram.org` напрямую.

---

## 1. Проект и сервисы

Установите CLI и войдите:

```bash
npm i -g @railway/cli
railway login
```

Создайте проект и свяжите с ним папку репозитория:

```bash
railway init          # назовите проект arumi
railway link
```

Дальше всё описано в [.railway/railway.ts](../.railway/railway.ts) — четыре
сервиса, их переменные и связи между ними:

```bash
railway config plan     # покажет, что будет создано и изменено
railway config apply    # применит после подтверждения
```

`plan` ничего не меняет. Посмотрите список и только потом применяйте.

> Файл проверен против живого Railway (коммиты 4bd1898, 5d8ec61, 2a5ae55):
> по нему развёрнут нынешний прод. Если `plan` покажет расхождение, сначала
> разберитесь, что именно меняется, и только потом `apply`. Регион
> существующего сервиса план не переносит — это делает
> `railway service scale`, подробности рядом с константой региона в файле.
>
> Если сервисы создаются в интерфейсе, а не планом, переменные ниже нужно
> вписать **все**, включая таблицу «Только для web»: план проставляет их сам,
> интерфейс — нет.

## 2. Переменные

Часть задаётся автоматически — `DATABASE_URL`, `REDIS_URL`, ключи бакета.
Остальное вы вписываете руками в интерфейсе Railway, в разделе Variables
каждого сервиса. **В репозитории их нет и быть не должно.**

**Одна переменная должна стоять раньше первой сборки — `RAILWAY_DOCKERFILE_PATH`.**
В репозитории два Dockerfile, и без неё оба сервиса соберут корневой: бот
получил бы образ витрины и упал бы на старте, потому что команды `pnpm bot` в
нём нет. `railway config apply` её проставляет, но если вы создаёте сервисы
руками — задайте до того, как нажмёте Deploy:

| Сервис  | `RAILWAY_DOCKERFILE_PATH` |
| ------- | ------------------------- |
| **web** | `Dockerfile`              |
| **bot** | `Dockerfile.bot`          |

Для **web** и **bot** одинаково:

| Переменная      | Что это                                                                                                                                                                                                                |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BOT_TOKEN`     | Токен от @BotFather. Только здесь, больше нигде                                                                                                                                                                        |
| `ADMIN_CHAT_ID` | Кому приходят уведомления о заявках: Telegram ID человека или id группы, куда добавлен бот (отрицательное число, обычно с `-100`). Подробнее — ниже                                                                    |
| `AUTH_SECRET`   | Подписывает сессии админки. `openssl rand -base64 32`, не короче 32 символов. **Одно и то же значение у web и bot**: web им подписывает, bot при старте проверяет длину и без неё не запустится. Никому не пересылайте |
| `MINI_APP_URL`  | Адрес, который Railway выдал сервису **web**, со схемой и без слэша на конце. Сейчас это `https://web-production-f03bf.up.railway.app`                                                                                 |
| `DEPLOY_TARGET` | `railway`. `vps` включает в `deploy:check` проверки домена и HSTS, которые здесь не имеют смысла                                                                                                                       |

Только для **web**:

| Переменная                 | Что это                                                                                                                                                                                                              |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ADMIN_LOGIN_REQUIRE_CODE` | `0` — вход в админку одним паролем, как просил клиент. `1` или пусто — пароль плюс код из Telegram, и тогда раздел «Как войти» в HANDOFF.md надо переписать обратно. Читается на каждом запросе, пересборка не нужна |
| `TRUSTED_PROXY_HOPS`       | `1` — перед витриной стоит один прокси Railway. От этого числа зависят лимиты входа и заявок по адресу                                                                                                               |
| `ENABLE_HSTS`              | `1` — HTTPS у Railway есть с первой минуты. **Вшивается при сборке**: Dockerfile принимает её как `ARG`, поэтому включается и выключается только новой сборкой web, не перезапуском                                  |

Необязательные:

| Переменная                      | Что это                                                                                                                                                                                                                                                           |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BOT_USERNAME`                  | Имя бота без собаки, только у web. **В проде не задана, и так и задумано**: кнопка «Поделиться» на странице товара даёт ссылку на сайт, и она открывает товар. Задана — ссылка ведёт в бота, `t.me/<бот>?start=p_<товар>`, и бот открывает каталог на этом товаре |
| `TELEGRAM_API_ROOT`             | Пусто — значит напрямую в Telegram. Заполняется, только если каталог переедет в РФ и понадобится релей                                                                                                                                                            |
| `NEXT_PUBLIC_YANDEX_METRICA_ID` | Номер счётчика Метрики. Пусто — Метрика не грузится вовсе. Вшивается при сборке, как и `ENABLE_HSTS`                                                                                                                                                              |

`MINI_APP_URL` появляется только после первого деплоя web — Railway выдаёт
адрес сервису при создании. Впишите его и передеплойте оба сервиса.

### `ADMIN_CHAT_ID`: куда приходят заявки

Уведомление о заявке отправляет **web** — именно его значение решает, куда
оно придёт. У bot держите то же самое: сам бот его не читает, но
`deploy:check`, который запускается в bot, проверяет переменную там — задана
ли и может ли бот писать в этот чат.

- **Один человек** — его Telegram ID. Узнать: человек отправляет боту `/id`,
  бот отвечает «Ваш Telegram ID: …».
- **Группа менеджеров** — добавьте бота в группу и отправьте в ней
  `/id@<имя бота>`; бот ответит «ID этой группы: …». С собакой и именем
  команда доходит до бота при любых настройках приватности группы.

Получатель должен сначала нажать у бота `/start`: бот не может написать первым
тому, кто ему ни разу не писал. После смены значения передеплойте web.
Проверка — одна пробная заявка от 5 000 ₽: сообщение с кнопкой «Открыть в
админке» должно прийти в этот чат. Потом переведите заявку в «Отменена».

Если уведомление не пришло, заявка не теряется: она на главной админки в
строке «Новые заявки» и в списке `/admin/orders`.

### Смена `AUTH_SECRET`

Меняйте, если значение хоть раз попало в переписку, в скриншот или в чужие
руки. Сгенерируйте новое у себя в терминале — `openssl rand -base64 32` — и
никуда его не вставляйте, кроме Railway. Задайте **одно и то же** новое
значение у web и у bot, передеплойте оба.

Цена — один повторный вход: все сессии админки, подписанные старым значением,
перестанут действовать, и каждый администратор войдёт заново. Больше ничего не
ломается: ни данные, ни бот. Выход из админки удаляет только куку в своём
браузере, поэтому смена секрета — единственный способ выйти отовсюду сразу.

## 3. Схема и проверка

Миграции накатывает сервис **bot** в `preDeploy` — у него полный образ с
исходниками и prisma CLI, а у витрины образ standalone, в котором ни того, ни
другого нет. Отдельного первого запуска руками не требуется: сборка витрины в
базу не ходит, так что порядок «сначала bot, потом web» достаточно соблюсти
один раз, выложив бота первым.

> **Все команды ниже — `railway ssh`, а не `railway run`, и всегда к сервису
> `bot`.** Две причины, и обе неочевидны. `railway run` выполняет команду на
> **вашей** машине, только подставив переменные сервиса, — а `DATABASE_URL`
> указывает на приватный адрес вида `postgres.railway.internal`, который
> снаружи кластера не резолвится; публичного адреса у базы намеренно нет.
> `railway ssh` выполняет команду **внутри контейнера**, где приватная сеть
> работает. И именно `bot`, потому что в образе витрины нет ни prisma CLI, ни
> каталога `scripts/`.

```bash
railway ssh --service bot pnpm deploy:check
```

Проверяет то, что ломается молча: переменные, локаль базы, миграции, Redis,
права на запись в бакет и доступность Telegram. Печатает, что делать с каждой
проблемой.

### Если ругается на локаль базы

Самое важное место во всём развёртывании.

Под `LC_CTYPE=C` расширение pg_trgm извлекает из кириллицы **ноль** триграмм:
поиск с опечаткой по-русски перестаёт работать полностью, а по-латински
продолжает — то есть дефект не виден, пока кто-нибудь не наберёт «шанел».

Локаль задаётся при создании базы и потом не меняется. На Railway до `initdb`
не добраться, но можно создать **отдельную базу** в том же кластере:

```bash
railway ssh --service bot pnpm db:create-ru
```

Затем в переменных **web** и **bot** замените имя базы в `DATABASE_URL` на
`arumi` и прогоните миграции:

```bash
railway ssh --service bot pnpm prisma migrate deploy
railway ssh --service bot pnpm deploy:check
```

Проверка также убеждается, что collation `ru-RU-x-icu` не просто числится, а
действительно сортирует: сборка PostgreSQL без ICU показывает её в
`pg_collation` и падает при использовании.

## 4. Первый администратор

```bash
railway ssh --service bot pnpm admin:create \
  --login magomed --telegram 123456789 --name "Магомед" --role OWNER
```

Пароль печатается один раз. Сохраните и передайте лично или голосом, не в
переписке. Без `--password` он генерируется — 24 случайных знака, и это
лучше любого придуманного: при входе одним паролем он единственная защита
панели.

**`--telegram` — собственный числовой Telegram ID клиента, не ваш.** Узнать его
клиент может сам: отправить боту `/id`. По этому числу бот показывает кнопку
«Админ-панель» и пускает в панель изнутри Telegram. С чужим числом `/admin`
отвечает «Эта команда доступна только администраторам», а вход из Telegram —
«Неверный логин или пароль», хотя тот же пароль с компьютера проходит.

**Эта команда — только для первого владельца.** Остальных владелец добавляет
сам в панели: «Админы» → «Добавить администратора»; там же меняет пароли и
отключает ушедших. Панель не даст завести второй раз тот же Telegram ID, а
команда даст: она ищет строку по `--telegram` и, если такая есть,
**перезаписывает** в ней логин, имя, роль и пароль. Повторный запуск с тем же
числом — это сброс пароля этого человека; запуск с вашим числом превращает
вашу строку в чужую. Роль по умолчанию — `OWNER`.

Проверьте после запуска: в «Админах» у вас и у клиента отдельные строки, у
каждого свой настоящий «Telegram ID», ваш вход по-прежнему работает. Затем
клиент отправляет боту `/start` — последней кнопкой под приветствием должна
появиться «Админ-панель». Нет её — число неверное, поправьте в «Админах» →
«Править».

Команда `/admin` появляется в меню команд бота только после его
перезапуска и только у тех, кто к тому моменту уже нажимал `/start`: при
старте бот прописывает её каждому администратору, а тому, кто ему ни разу не
писал, прописать не может. Кнопка под `/start` и набранная руками `/admin`
работают сразу. Поэтому после того, как новый администратор нажал `/start`,
перезапустите bot в Railway (Deployments → Restart), если хотите, чтобы
команда была у него в меню.

## 6. Бот в BotFather

Настраивать почти нечего. Команды (`/start`, `/catalog`, `/contacts`, а
администраторам ещё `/admin`) и кнопку меню «Каталог», ведущую на
`MINI_APP_URL`, бот ставит сам при каждом запуске — и перезапишет то, что
задано через `/setmenubutton`. `/setdomain` тоже не нужен: входа через
Telegram-виджет на сайте нет.

В [@BotFather](https://t.me/BotFather) остаются имя бота, описание и картинка —
как захочет клиент: `/mybots` → бот → Edit Bot.

`/id` намеренно не в меню: покупателю он ни к чему. Это служебная команда —
она сообщает человеку его Telegram ID, а в группе — id группы.

**Кому принадлежит бот.** Бот — актив бизнеса: вместе с аккаунтом, на котором
он зарегистрирован, теряются и он, и все переписки с покупателями. Если он
создан с вашего аккаунта, а владеть им должен клиент, передайте его:
`/mybots` → бот → Bot Settings → Transfer Ownership. Так же решите, в чьём
аккаунте Railway живёт проект: если клиент завёл свой, перенесите проект туда.

## 7. Обновление

```bash
git push        # Railway собирает и выкладывает сам
```

Миграции применяются автоматически: они в `preDeploy`, то есть выполняются
один раз между сборкой и запуском, и неудачная миграция останавливает выкладку
вместо того, чтобы поднять приложение на половине схемы.

Если менялись сервисы или переменные — `railway config plan` и `apply`.

## 8. Резервные копии

**Регулярные — от Railway.** Включите бэкапы у сервиса Postgres в интерфейсе.
Они снимаются по расписанию и хранятся без вашего участия. Проверьте, что
включены: это одна галочка, про которую забывают.

**Ручная копия — перед рискованным:**

```bash
railway ssh --service bot ./scripts/dump.sh
```

Кладёт файл в `./backups/` **внутри контейнера**, поэтому сразу заберите его
к себе — контейнер переживёт не всякую выкладку. Забирать копию стоит перед обновлением схемы,
массовым импортом и вообще перед всем, что страшно.

Восстановить:

```bash
pg_restore -d "$DATABASE_URL" --clean --if-exists --no-owner backups/arumi-….dump
```

**Потренируйтесь один раз** на пустой базе. Бэкап, который никто ни разу не
восстанавливал, — это надежда, а не бэкап.

## Что смотреть, когда что-то не так

```bash
railway logs --service web
railway logs --service bot
```

| Симптом                                                                                              | Обычная причина                                                                                                            |
| ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Сборка web падает на «Can't reach database server»                                                   | Не должна: сборка в базу не ходит. Значит, добавилось чтение без `io()` — см. раздел про `io()` в CLAUDE.md                |
| Бот запускается и сразу падает                                                                       | Неверный `BOT_TOKEN`, либо Telegram недоступен                                                                             |
| Бот падает с «Command "bot" not found» или сразу после сборки                                        | У сервиса bot не задан `RAILWAY_DOCKERFILE_PATH=Dockerfile.bot` — он собрал образ витрины                                  |
| Поиск не находит по-русски с опечаткой, по-латински находит                                          | Локаль базы не UTF-8 — раздел 3                                                                                            |
| Фотографии не показываются                                                                           | Сервис web не видит бакет: проверьте `S3_*` в его переменных                                                               |
| Кнопка каталога в боте ведёт в никуда                                                                | Не задан `MINI_APP_URL`                                                                                                    |
| Заявки приходят, уведомлений нет                                                                     | `ADMIN_CHAT_ID` у web не задан или чужой, получатель ни разу не нажимал `/start` у бота, либо бота нет в группе — раздел 2 |
| Клиент не видит «Админ-панель» в боте; из Telegram «Неверный логин или пароль», с компьютера пускает | В «Админах» у клиента не его Telegram ID — раздел 4                                                                        |
| Вход в админку просит код из Telegram                                                                | `ADMIN_LOGIN_REQUIRE_CODE` у web не `0`                                                                                    |
| `/admin` нет в меню команд у нового администратора                                                   | Бот прописывает её при старте — перезапустите bot после того, как человек нажал `/start`                                   |
| web перезапускается по кругу                                                                         | `/api/health` не отвечает: база недоступна                                                                                 |

# Запасной вариант — свой сервер в РФ

Если из России витрина будет открываться медленно, всё переезжает на VPS в РФ.
Это готовый и **проверенный запуском** путь: `docker-compose.prod.yml`
поднимается, все сервисы healthy, `deploy:check` проходит.

Отличия от Railway:

- **Нужен релей за пределами РФ** — `api.telegram.org` с российского хостинга
  недоступен. Конфиг и инструкция: [relay/README.md](../relay/README.md).
  Без него не работает ничего телеграмного: ни приветствие, ни уведомления о
  заявках, ни код входа в админку, если он включён.
- **Нужен свой домен** и две A-записи: на сервер и на релей. Домен обязан
  резолвиться **до** первого запуска — Caddy выпускает сертификат через ACME, а
  тот проверяет, что домен уже ведёт сюда.
- **Нужно объектное хранилище** — Yandex Object Storage, VK Cloud, Selectel.
  С публичным чтением: тогда браузер забирает фотографии напрямую, минуя
  приложение. Адрес бакета кладётся в `NEXT_PUBLIC_S3_PUBLIC_URL`, и прокси
  `/api/media/…` сам собой перестаёт использоваться.

Порядок:

```bash
cp .env.production.example .env.production   # заполнить, chmod 600
./scripts/deploy.sh                          # поднимет всё в правильном порядке
DEPLOY_TARGET=vps docker compose -f docker-compose.prod.yml \
  --env-file .env.production run --rm --entrypoint "" migrate pnpm deploy:check
```

`deploy.sh` поднимает всё по порядку: база, схема, сборка, запуск. Написан он
был, когда `next build` под `cacheComponents` ещё ходил в PostgreSQL; теперь
сборка в базу не ходит (раздел про `io()` в CLAUDE.md), но порядок «сначала
схема, потом приложение» по-прежнему правильный.

`ENABLE_HSTS` на своём сервере — только после того, как HTTPS заработал и
проверен: браузер запомнит запрет на год. Он вшивается при сборке витрины,
так что после включения соберите web заново.

Регулярные копии там делает `scripts/backup.sh` (cron, выгрузка в бакет,
хранение 14 дней), восстановление — `scripts/restore.sh`.
